# 方案多视角评审报告（归档）

> 2026-08-18 · 产品 / 架构 / 数据源 / Agent&记忆 / 排序 5 视角工作流汇总 + 终端用户视角。作为 01-requirements 修订的决策依据。

# 个人技术情报台方案评估报告

## 1. 总体判断

方案**成立**：核心决策（DB 真相源 + Obsidian 单向投影、规则先筛再进 LLM 的分级成本、DB 表做任务队列、Telegram 日报为主入口、Day1-5 最薄闭环）五个视角一致认可。但存在三个共性问题：

1. **P0 严重超载，与 MVP 路线自相矛盾**：P0 列了 6 种源、六因子排序、四视图、Web 四页、语义检索、Telegram 双向指令，远超 Day1-5 能交付的范围（架构、产品视角）。
2. **排序公式不可落地**：五因子连乘对零值/极值敏感、各平台指标量纲未定义归一化方式、增速/时间语义缺失、P0 阶段"个人相关性"为空（排序、架构、数据源三视角一致）。
3. **最脆弱的部分被放在 P0，最必要的护栏放在 P1**：DailyHotApi/wewe-rss/RSSHub/twitterapi.io 都会静默失效，而源健康监控是 P1；实体消歧、embedding 供应商、结构化输出格式等基础决策缺失。

## 2. 高严重度风险（合并）

| 风险 | 来源视角 | 改进建议 |
|---|---|---|
| **P0 范围过大** | 产品、架构 | P0 = 3 个稳定源 + canonical 去重 + 简单打分 + 一次调用摘要/打标 + Telegram 单向日报 + 收藏/忽略。验收标准：连续 7 天收到愿意看完的日报 |
| **排序公式：连乘、归一化/增速未定义、冷启动为空** | 排序、架构、数据源、产品 | 改为对数域加权求和，缺失因子给中性值；平台内用滚动 14 天分位数归一；增速按平台分快变/慢变；P0 相关性只用规则版（关键词/作者/领域）；每因子拆开存储并展示"为什么排这里" |
| **源脆弱且无监控** | 数据源、产品、架构 | 源健康记录（last_success/consecutive_failures/条目数）提到 Day1；日报尾部一行告警；自托管 RSSHub/DailyHotApi；fetcher 基类内置限流与指数退避；公众号/X 后置，公众号只做作者白名单源不参与热度 |
| **跨平台去重定义不足** | 架构、数据源、Agent、排序 | 第一层确定性 canonical_key（短链展开、去 utm、GitHub owner/repo、arXiv id、DOI）硬合并；相似合并 P1 用 embedding ≥0.9 + 48h 窗；数据模型拆 items / item_sources，快照挂 item_sources；跨平台加成 MVP 只对硬合并生效 |
| **中途换库 SQLite→Postgres** | 架构 | Day1 直接 docker 起 Postgres+pgvector，或全程 SQLite；不要过渡态 |
| **实体消歧未设计** | Agent、产品 | 实体表加 canonical_name + aliases + 外部锚点；P1 只对订阅中显式声明的白名单实体建档；开放抽取 + 别名合并 + Telegram 人工确认推 P2；合并可撤销 |
| **LLM 输出格式/embedding 未定** | Agent、架构 | 摘要+打标+实体+相关性合并为一次结构化输出调用（封闭枚举）；embedding 在 Day5 前定模型（bge-m3 或 Voyage）并记录版本 |
| **日报无容量约束** | 产品 | Top 5 必读 + 折叠 ≤10 条订阅命中 + 一句话总结，手机一屏半；条数上限写入 P0 验收 |

## 3. 功能推荐清单

**P0**
- items/item_sources 两层模型 + canonical_key 去重：所有下游能力的地基，Day3 前定好避免返工。
- 管线状态机（new→enriched→scored→digested）+ 幂等 job：崩溃/限流后靠状态恢复。
- 最小源健康监控 + 日报尾部告警：防止情报台"半瞎"而不自知。
- fetcher 基类限流/退避/月预算：避免简单重试加速封禁。
- RawItem 三时间字段（published/first_seen/last_seen）+ metrics_raw + content_level：时间衰减与摘要质量依赖，事后补填成本高。
- 统一 LLM 调用层 + 一次调用合并结构化输出 + usage 记账（日报显示当日花费）：成本降 1/3、消灭解析失败、账单可见。
- 日报"入选原因"标签 + 条数硬上限 + 排序分解视图：3 秒判断是否点开，也是唯一调参依据。
- 反馈特征快照宽表 + ranker_version：P0 收第一条反馈前建好，否则前几周数据报废。
- 反馈即时可感（忽略即隐藏相似项、"更少"直接给标签乘子）：养成反馈习惯。
- 收藏 Inbox（Telegram 收藏按钮 ↔ Web）：收藏否则变黑洞。

**P1**
- 手动投喂（Telegram 转发链接 /add）：灰色源失效的兜底 + 最强兴趣信号。
- 事件折叠/同题合并 + 摘要调用同时输出 entities/event_key：跨平台重复是过载主因，且聚类零额外调用。
- 混合检索（tsvector + pgvector）+ Chat 出处强校验：精确项目名靠 BM25，引用 ID 白名单防幻觉。
- Batches API 离线摘要：半价且不占调度。
- 实体消歧管线（白名单实体优先）。
- 订阅可视化调参页 + 探索配额（20%）+ 对比式 LLM 分档：解决冷启动与兴趣过窄。
- 周报 + 每周排序评估报表（precision@N、漏召回、来源熵）：迭代方向的唯一依据。
- 研究报告固定 schema + 任务预算/步数上限 + 来源审计段。
- HF papers / GitHub releases Atom / changelog RSS 补充源：官方接口稳定，补齐 arXiv 无指标问题。

**P2**
- 作者/来源权重基于反馈的贝叶斯校准；简单线性/GBDT 精排替代手调权重（需先攒数据）。
- 开放式实体抽取 + 别名合并。

## 4. 建议砍掉/推迟

- **砍**：SQLite→Postgres 两阶段；独立翻译步骤（摘要直接中文输出）；LLM 0-10 绝对打分；兴趣画像自动学习/隐式反馈/记忆衰减；Notion 导出/RSS 输出；浏览器插件投喂；泛社会热榜（微博/知乎/抖音）；JS 渲染反爬抓取。
- **P0→P1**：Web 四页面（Web 只做 HTMX 只读列表）；embedding 语义检索；多视图与筛选（只留一个流）；订阅 YAML/作者权重表；Telegram /dig /search 指令；公众号与 X 源；快照参与增速排序。
- **P1→P2**：开放式实体抽取；上升话题榜（需 4 周基线 + 实体）；移动端适配。

## 5. 架构与 MVP 修改建议

架构调整：前端定为 HTMX + Jinja2（同一模板渲染 Web 与 Obsidian MD）；管线拆 fetch(小时)/enrich(pending 表驱动)/digest(每日) 三个幂等 job；Obsidian 每日批量渲染 + hash 比对，用户笔记用 HTML 注释标记或独立 notes 文件；模型分级 Haiku 4.5 摘要 / Opus 5 研究，prompt 前缀开缓存；快照按条目年龄分层回访、只在变化时写、>7 天降采样。

**修改后 MVP 路线**（约 3 周）：
- **W1 Day1-2**：Postgres+pgvector 容器；items/item_sources/snapshots/source_health 表；fetcher 基类（限流/退避/健康记录）；HN Algolia + GitHub(REST 单点回访) + 1 个 RSS。
- **Day3**：canonical_key 归一去重；状态机；三时间字段。
- **Day4**：规则排序（订阅命中优先 + 分位数热度 + 时间衰减）；各因子拆开存储。
- **Day5**：一次调用结构化摘要/打标（Haiku）；LLM 记账；Telegram 单向日报（Top5 + 折叠 ≤10 + 入选原因 + 源告警 + 当日花费）；inline 收藏/忽略按钮；反馈宽表。
- **W2**：跑满 7 天，观察日报可读性与源稳定性；加 arXiv/HF papers/releases；Batches API；Telegram /add 投喂；HTMX 只读 feed + Inbox。
- **W3**：embedding + 事件折叠；白名单实体档案；订阅调参页；周报与评估报表；研究助手模板化 /dig。
- 之后按评估指标决定是否接公众号/X、开放实体抽取、上升话题榜。

## 6. 视角间分歧

- **事件聚类时机**：排序视角主张 embedding 轻量聚类提前到 P0（否则跨平台加成永远触发不了）；Agent 与架构视角认为聚类依赖已消歧实体，应放 P1。**裁决**：P0 只做 canonical_key 硬合并并按此计算跨平台加成，embedding 折叠放 W3，聚类的 LLM 判定放实体层稳定之后。
- **快照写入**：排序/数据源视角认为 P0 必须记快照；产品视角建议 P0 不投入。**裁决**：P0 记录（表结构便宜），但不参与排序，增速作为展示字段。
- **Web 在 P0 的角色**：架构视角主张 Web 全推 P1；产品视角要 Web 详情深链与 Inbox。**裁决**：W2 起做 HTMX 只读列表 + Inbox，不做实体页/搜索。
- **反馈机制**：架构视角主张确定性规则（×0.5、收藏向量最近邻）；排序视角主张宽表 + 后续 GBDT。两者不冲突：P0/P1 用规则，宽表为 P2 模型留数据。

# 附：终端用户视角评审（摘要）

**总体评价**：架构扎实但"系统视角"重、"15 分钟视角"轻，容易做成自己不天天打开的仪表盘。

**Top 5 改进**：
1. 日报硬限 ≤8 条 + Telegram 内联按钮闭环，Web 只是延伸
2. Web 默认单流"今日未读"，隐藏筛选和分数，未读自动过期
3. "模糊描述→找回旧条目"作为核心场景，语义搜索接入 Telegram（发文字即搜索）
4. 隐式反馈提到 P0，删掉"更多/更少这类"；砍掉全量热榜、事件聚类前置、笔记回写
5. 实体时间线改为"收藏过的东西有新动静时主动提醒"，而不是让用户去看档案页

**最想要但原方案没提**：Telegram 内联按钮 + 发消息即搜索；未读自动过期；中英去重 + "国内独有/海外独有"标记；收藏时一句备注 + 按实体归组；`/mute 某来源 7 天`。

# 后记：内核选型（2026-08-18）

评估了 Hermes Agent（Nous Research，全功能 agent runtime，含记忆/skills/cron/Telegram 网关）与 pi（Mario Zechner，TS 极简 agent harness）作为内核的可能性。结论：**都不采用**。TechRadar 80% 是确定性数据管线 + 结构化记忆，agent 只占 20%；Hermes 的记忆模型与我们的 items/entities/feedback 宽表冲突、且管线不该跑在 LLM runtime 里、其 API 高速演进对单人项目是负担；pi 语言错配且面向编码场景。采纳 pi 的"最小内核 + 钩子"哲学用于 fetcher/pipeline 插件设计。核心能力通过 MCP server 暴露，为未来接入任何前门保留零成本路径。
